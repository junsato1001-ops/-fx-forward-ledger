# M1-MACRO Transformation Spec — Part 2-A: Missing-feature Policy(案 v0)

- 状態: **v1 FREEZE CANDIDATE**(Claude、2026-10-17)。v0 に対するむすびの監査(2026-10-17 03:15 JST、CONDITIONAL PASS)の修正3点を反映した。
- v0 からの変更:
  1. F_POS の15日の上限をやめた。Freeze 済みの公表日の再構築から古さを判定する(§2.3)。ただし、むすびの案の「次の報告の公表時刻の上限」を古さの判定に使うと、政府閉鎖の間に古い報告を使い続ける穴が残る。そこで、先読みを防ぐ時刻(Usable_From)と、古さを判定する時刻(Expected_Release)を分けた。
  2. 欠測の説明を、市場の状態と独立とは仮定しない形にした(§3-3)。
  3. EVAL-SPEC との関係の記述を正確にした(§3-2)。
- 前提:
  - M1-MACRO-DATA-AVAILABILITY-V1(Freeze 済み)
  - M1-MACRO-TRANSFORM-PART1-V1(Freeze 済み、SHA-256 42918ab8…)
  - EVAL-SPEC-V1(Freeze 済み)
- 封印: 候補系列の値、欠測の実際の件数や時期の分布、成績は見ていない。
- 範囲: 特徴量が欠けたときの扱いだけを決める。どのペアにどの特徴量を入れるか(Pair-specific feature set)は Part 2-B で決める。この文書では、それを記号 N(p) で表す。

## 1. 2つの問題を分ける(むすびの指摘)

| | 意味 | 決める場所 |
|---|---|---|
| **通常の特徴量の集合 N(p)** | ペア p について、M1-MACRO-V1 が**常に**使う特徴量の集合。例: 米ドル円は F_US・F_JP・F_POS、米ドル以外の円クロスは F_JP・F_POS(案) | Part 2-B |
| **代わりの部分集合(fallback subset)** | N(p) の一部が取れないときに、残りだけで予測すること | この文書 |

N(p) がペアによって違うことは、モデルの定義そのものである(事前に固定する)。一方、時期によって使う特徴量が変わるのは、同じ名前で別のモデルを切り替えることになる。この文書は後者を禁止する。

## 2. 方針(案)

### 2.1 中心の規則: 特徴量を黙って落とさない

M1-MACRO-V1 が (p, Origin D, Horizon h) で FORECAST を出せるのは、**N(p) のすべての特徴量が、Origin D の T_info で point-in-time に定義できるときだけ**である。

1つでも欠けたら、M1-MACRO-V1 はその機会に予測を出さない。次のことはすべて禁止する:

| 禁止すること | 理由 |
|---|---|
| 残りの特徴量だけで予測する(部分集合への切り替え) | 同じ名前で別のモデルになる。ペアごとの集合に部分集合が加わると、モデルの種類が急に増える |
| 欠けた特徴量を 0 や平均などで埋める | 0 を入れるのは「その特徴量の情報がない」という仮説を黙って入れるのと同じで、部分集合への切り替えと実質は変わらない |
| 許容された古さ(Matrix の規則)を超えて、古い値を使い続ける | Matrix V1 §5 で禁止済み |
| 親モデル(S0 または M1-VOL)の予測を M1-MACRO の行として出す | Matrix V1 §5 で禁止済み。親と成績が混ざり、検定の意味が崩れる |
| 欠けた特徴量の係数だけを 0 にして予測する | 0 で埋めることと同じ |

### 2.2 欠けたときの Decision_Class

| 欠けた理由 | Decision_Class | Reason_Code(案) |
|---|---|---|
| 系列がまだ存在しない(例: F_POS は Origin 2010-12-08 より前) | MODEL_PREREQ_UNAVAILABLE | FEATURE_NOT_YET_AVAILABLE |
| Gate で使えないとした期間(CFTC の政府閉鎖など、Matrix §3) | MODEL_PREREQ_UNAVAILABLE | FEATURE_GATE_EXCLUDED |
| ソース側の公表が遅れ、許容された古さを超えた(STALE) | MODEL_PREREQ_UNAVAILABLE | FEATURE_STALE |
| 変化を計算できない(20 source-business-days 前の値がない、総建玉が 0 または欠けている) | MODEL_PREREQ_UNAVAILABLE | FEATURE_NOT_COMPUTABLE |
| 本番で取得そのものに失敗した(fetch / parse の失敗) | ABSTAIN_SYSTEM | FEATURE_UNAVAILABLE |

分け方は Matrix V1 §5 と、むすびが承認した手順に従う。まず fetch / parse が成功したかで分け、成功したのに期待する値の日付がなければ、ソース側の遅れとして古さを判定する。

### 2.3 F_POS の古さの判定(固定の日数を使わない)

v0 の「報告の基準日から15日」はやめる(むすびの監査)。Freeze 済みの CFTC の公表日の再構築(Matrix V1 §3、CFTC Gate)から、機械的に決める。

報告 R_k(基準日の順に k = 1, 2, …)ごとに、2つの時刻を区別する。

| 時刻 | 定義 | 使い道 |
|---|---|---|
| **Usable_From(R_k)** | 公表時刻の上限(Matrix V1 §3)。Gate で使えないとした報告は「なし」 | **先読みを防ぐ**。T_info ≥ Usable_From の報告だけを使う |
| **Expected_Release(R_k)** | 政府閉鎖などの例外がなかった場合の、**通常の公表規則での**公表時刻。基準日の週の金曜 15:30 ET。火〜金に連邦の祝日がある週は、翌週の月曜 15:30 ET(Matrix V1 §3 の 3) | **古さを判定する** |

規則:

- Origin D で F_POS に使う報告は、Usable_From ≤ T_info(D) を満たす最新の報告 R_k とする。
- 次の報告 R_{k+1} について、**Expected_Release(R_{k+1}) ≤ T_info(D) < Usable_From(R_{k+1})** のとき(出るはずの時刻を過ぎたのに、まだ使えないとき)は、F_POS = FEATURE_STALE とする。
- R_{k+1} の Usable_From がない(Gate で使えないとした報告)ときは、Expected_Release(R_{k+1}) ≤ T_info(D) となった時点から、使える次の報告が出るまで FEATURE_GATE_EXCLUDED とする。
- 本番では、Expected_Release を CFTC の公式の公表日程(Release Schedule)と特別告知から決める。過去の再構築では、通常の公表規則から決める。どちらも事前に分かる情報だけを使う。

**2つの時刻を分ける理由**: 公表時刻の上限は、先読みを防ぐために安全側(遅め)に取っている。たとえば 2013年の政府閉鎖では、溜まった報告をすべて 2013-11-08 から使うことにした。この上限を古さの判定にも使うと、閉鎖の間ずっと、9月24日基準の報告が「古くない」ことになる。古さは、本来出るはずだった時刻で判定しなければならない。

**結果**:

| 場合 | 判定 |
|---|---|
| 通常の週・祝日の週 | Usable_From = Expected_Release なので、STALE にならない |
| 政府閉鎖・catch-up | 本来の公表時刻から、報告が使えるようになるまでの間は STALE、または GATE_EXCLUDED |
| 誤って早く公表された報告(2014-07) | Usable_From は予定の日なので、影響しない |
| 基準日が月曜・水曜の不規則な週 | 同じ規則で扱える |

### 2.4 学習(係数の推定)に使う過去の機会

係数の推定には、N(p) のすべての特徴量がそろっていた過去の機会だけを使う(complete case)。欠けた機会を学習のために埋めることもしない。推定の詳細と最低の標本数は Model Spec で決める。

## 3. 結果として決まること

1. **ペアごとの開始日**は、N(p) の各特徴量の利用開始のうち最も遅いものになる。Part 2-B で N(p) が決まれば、機械的に決まる。
   - N(p) に F_POS が入れば、そのペアの M1-MACRO-V1 は Origin 2010-12-08 以降だけで予測する。
2. **EVAL-SPEC-V1 との関係**:
   - MODEL_PREREQ_UNAVAILABLE は Decision coverage(FORECAST / (FORECAST + ABSTAIN_MODEL))の分母に含めないので、カバレッジの非劣化の判定(親から −2.0pp まで)を直接は下げない。一方で、Prerequisite readiness を下げ、モデル比較の共通標本を制限しうる。
   - 親との比較は、共通標本(比べる全モデルが FORECAST で、結果が OBSERVED)で行う。したがって、比較は M1-MACRO-V1 の特徴量がそろう期間だけで行われる。
3. **注意(評価の解釈)**: 特徴量が使えないことが、市場の状態と独立であるとは仮定しない。したがって、M1-MACRO-V1 の性能評価は共通標本の上での条件付きの性能として解釈し、Prerequisite readiness と Operational completion を性能の指標と必ず並べて報告する(EVAL-SPEC-V1 §4.2)。

## 4. 代わりの案と、採らない理由

| 案 | 採らない理由 |
|---|---|
| 事前に決めた部分集合で予測する(例: F_POS がなければ F_US・F_JP だけ) | 同じ名前で時期によってモデルが変わる。部分集合ごとに係数の推定と評価が必要になり、比較の数が増える(多重比較)。必要なら、部分集合ごとに**別のモデル名**の別 Trial として事前登録する |
| 欠けたときは親モデルと同じ予測を出す | 親と成績が混ざる。Matrix V1 §5 で禁止済み |
| F_POS の古さを上限なしにする | 政府閉鎖の間に数週間前の報告を使い続けることになり、Gate で意図した保守的な扱いと矛盾する |
| F_POS の古さを固定の日数で決める(v0 の 15日) | 公表の規則から導いても、すべての例外を覆うとは言えない。Freeze 済みの公表日の再構築から決める方が、規則が1つで済む |
| 公表時刻の上限(Usable_From)だけで古さも判定する | 上限は先読みを防ぐために遅めに取っているので、政府閉鎖の間に古い報告を「古くない」と判定してしまう(§2.3) |

## 5. Model Spec に送る論点(ここでは決めない)

- **係数の推定がまだできない時期(warm-up)**に、係数を 0 にして親と同じ予測を出すか(M1-VOL の DEFAULT_PARENT と同じ扱い)、MODEL_PREREQ_UNAVAILABLE にするか。
- 区別: warm-up の時期は、特徴量の値はすべてそろっていて、推定の規則が事前に決めた形で係数を 0 に縮めているだけである。特徴量が欠けたときに係数を 0 にする(この文書で禁止したこと)とは別の問題として扱う。

## 6. 実装の注記(Freeze の条件ではない)

- 同じ Reason_Code の中でも、監査用に細かい理由(subreason)を分けて保存する。例: FEATURE_NOT_COMPUTABLE の中で「総建玉が 0」と「総建玉が欠けている」、FEATURE_STALE の中で「金利(公表営業日の古さ)」と「CFTC(Expected_Release を過ぎた)」。
- Expected_Release と Usable_From は、報告ごとに記録として保存する。
