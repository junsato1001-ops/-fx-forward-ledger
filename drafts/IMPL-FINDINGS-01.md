## 確認事項 2: 本番の Usable_From の安全性(仕様の追加が必要かもしれない点)

Freeze 済みの Impl Part 1 §2.3 では、Usable_From を規則 ①〜⑤ と config の表(例外・祝日)で決め、表にない例外を実行時に推測で加えない。過去の再構築ではこれで安全である。

**本番では穴がある**: 今後、config の表にない遅れ(新しい国葬・閉鎖・臨時の遅れ)が起きると、規則 ⑤ が「金曜 15:30 ET」を返す。一方、実際の公表は、たとえば月曜 15:30 ET(= 火曜 04:30 JST、夏時間)になる。取得は T_info(03:00 JST)より後の 04:40・06:40・07:55 JST に行うので、**T_info の後に公表された報告が取得したファイルに入り、規則上は使えると判定されてしまう**(先読み)。

案(どれも情報を減らす方向にだけ働く):

- (a) 本番の Usable_From = max(規則 ①〜⑤ の値、取得した公式の Release Schedule と特別告知の予定時刻)。予定が規則より遅ければ予定を使う。
- (b) (a) に加えて、取得した特別告知のページの内容が前回の取得から変わった場合は、その Run では F_POS を ABSTAIN_SYSTEM(FEATURE_UNAVAILABLE)にし、人が config の表を更新する(新しい Version)まで待つ。
- (c) T_info より前の実行(forward.yml の 02:40 JST)で CFTC のファイルを取得して保存し、**T_info より前の取得に含まれていた報告だけ**を使う。公表が T_info 以前だったことの直接の証拠になる。cron の遅れで 03:00 を過ぎた場合は、その Origin では前の報告までしか使えない(STALE の判定は Expected_Release で行うので、STALE になりうる)。

私の推奨: **(c)**。規則や告知の解釈に頼らず、「T_info 以前に実際に存在した」ことを記録で示せる。ただし Freeze 済みの Impl Part 1 の規則を変えるので、Impl Part 1 の新しい版(V1.1)として事前に登録する必要がある。(a) だけでも大半の場合は防げるが、告知のない遅れは残る。
