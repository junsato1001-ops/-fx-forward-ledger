## 確認事項 1: 本番での「期待する値の日付」と古さの数え方(実装上の解釈が必要)

Impl Part 1 V1.1 は、公表営業日の暦を「その系列に値がある日付の集合」と定める(§1)。過去の再構築ではこれで決まり、古さは起きない(Matrix §5 注2)。

本番では、まだ公表されていない日は系列に現れないので、「期待する値の日付」(米国債: D−1 より前の最後の公表営業日、財務省: D より前の最後の営業日のさらに前の営業日)と、「公表営業日で 2 日まで」の古さを、系列の日付だけでは決められない。

案:

- (A) **期待する公表日の暦を規則で作る**。米国 = 連邦の営業日(5 U.S.C. 6103 の祝日と、Impl Part 1 V1.1 §2.3.2 の臨時の休み)。日本 = 銀行の営業日(国民の祝日に関する法律の祝日・振替休日・国民の休日と、12/31〜1/3)。本番の期待する値の日付と古さの日数は、この暦で数える。20 日前(v−20、u−20)は V1.1 のとおり系列の日付で数える。
  - 系列に、期待の暦では営業日でない日の値がある(または逆)場合は、値は使い、記録だけ残す(暦の差は古さの数え方にだけ影響し、値には影響しない。Matrix §5 注3)。
  - 将来の祝日の変更(法改正、臨時の祝日)は config の表の更新になり、新しい Version が必要になる。それまでの間に暦がずれると、古さの判定が1日ずれることがありうる(値の先読みにはならない。値の日付の規則と公表の余裕は別に効いているため)。
- (B) 古さを暦日で数える(例: 期待する値の日付から 4 暦日)。暦が要らないが、Freeze 済みの「公表営業日で 2 日」とは違う規則になる。

私の推奨: **(A)**。Freeze 済みの文言(公表営業日で数える)に最も近い。(B) は仕様の変更になる。

## 確認事項 2: CFTC の TLS の証明書(実装上の対応、報告)

固定したイメージ(python:3.12.7-slim-bookworm)の中から www.cftc.gov に接続すると、証明書の検証に失敗する。CFTC のサーバーの証明書は Sectigo Public Server Authentication Root R46 につながるが、このイメージの CA の一覧にこのルートが入っていない(GitHub の Ubuntu の runner では検証に成功する)。

対応の案: **検証を切ることはしない**。Sectigo Public Server Authentication Root R46 のルート証明書(公開情報)を、SHA-256 の指紋を固定して config に入れ、CFTC への接続だけ、既定の CA の一覧にこの1つを加えた検証で行う。指紋は一次資料(Sectigo と CCADB の公開値)と照合してから固定する。データの意味には関わらない、通信の実装の話なので、仕様の変更ではないと考えるが、念のため報告する。

## 確認事項 3: Inauguration Day(報告)

米国の連邦の祝日に、Inauguration Day(5 U.S.C. 6103(c)。CFTC の所在地のワシントン D.C. 地域の連邦職員に適用)を含めた。CFTC の規則 ③(火〜金に連邦の祝日がある週は翌週の月曜)の判定で、2017-01-20(金)の週と 2021-01-20(水)の週が「祝日の週」になり、Usable_From と Expected_Release が翌週の月曜になる。上限を遅い側にするだけなので、先読みにはならない。
