## 2. 守る原則

1. **V1 は変更しない。** V1 の workflow・時刻・取得経路・Code_SHA に、後から手を加えない。V1 の Forward はそのまま続け、観測を貯める。
2. **V1 と V2 を分離する。**
   - V2 の設計・試験・試験取得の結果は、V1 の本番データ(data/m1macro/)にも台帳(ledger/m1_macro_*)にも混ぜない。
   - V2 のデータは、別の path、別の branch、または別の repository に置く(物理的な分離)。
   - V2 のデータには、V2 の検証用 telemetry であるという区分を付ける(論理的な分離)。
3. **救済しない。** V2 の仕組みで取得した snapshot を、V1 の発行に使わない。V1 は V1 の凍結した規則だけで判定する。
4. **統計仕様は変えない。** V2 で変えるのは取得と trigger だけ。CFTC Forward Snapshot Gate の意味(下の §3)は変えない。
5. **事前に決めた基準で評価する。** V2 の Acceptance Gate(§7)の閾値は、V2 の試験 telemetry を見る**前に**固定する。
6. **単一障害点を減らす。** 「cron の時刻を早めれば解決する」とは決めない。遅れや抜けが今後どうなるかは分からないという前提で設計する。

## 3. CFTC の取得の窓(凍結済みの規則。V2 でも変えない)

- Origin t の CFTC snapshot として使えるのは、取得の時刻 Retrieved_At が **(T_info(t) − 6h, T_info(t)]** の範囲にあるものだけ(Impl Part 1 V1.2 §2.3.1、cftc_feature.forward)。
- T_info(t) は Origin の日の 03:00 JST。窓は前日の 21:00 JST から当日の 03:00 JST まで(UTC では 12:00Z 〜 18:00Z)。
- 窓の中に複数の取得がある場合は、最も遅いものを使う(Retrieved_At と SHA-256 で決める)。
- **確認しておく点**: V1 の Retrieved_At は、runner の上で取得した時点の時計の値である。V2 でも同じでよいか、それとも server 側の時刻(取得を記録した commit の push 時刻など)を併せて記録するかは、§6 の監査可能性の論点になる。

## 4. 現在の trigger の構造(V1)

| 段 | trigger | 役割 |
|---|---|---|
| CFTC の pre-T_info snapshot | GitHub Actions の `schedule`(15:40Z、17:40Z) | 窓の中で CFTC の原ファイルを取得し、main に追記する |
| M1 の発行 | `workflow_run`(S0 の forward-ledger が success になった後) | Treasury・MOF・CFTC の公表予定を取得し、特徴量・推定・予測を計算して、台帳の transaction を行う |
| S0 の発行 | GitHub Actions の `schedule`(S0 側) | S0 の行を発行する。M1 の発行はこれが前提になる |

構造上の弱点として、次の 2 点がある。

- CFTC の取得が、GitHub の `schedule` という 1 つの仕組みに依存している。窓の終わりに近い 2 回しか予定がない。
- M1 の発行が S0 の `schedule` の成功に依存している。M1 の起動が S0 に連なっている。

## 5. 候補

| # | 候補 | 内容 |
|---|---|---|
| A | 窓の中で早めに、何度も cron を置く | 例: 12:10Z から 17:50Z まで 30〜60 分おきに置く。各回は冪等にする(窓の中の取得が 1 つ以上あれば足りる) |
| B | 起動した 1 つの job が、窓の中で何度も取得する | 窓の前から窓の終わりまで動く長い job が、一定の間隔で取得を繰り返す。起動が 1 回成功すれば、窓の中で何度も取得できる |
| C | GitHub の外の scheduler から起動する | 外部の scheduler(cloud の scheduler など)が `workflow_dispatch` または `repository_dispatch` で起動する。GitHub の schedule には依存しない |
| D | self-hosted runner や外部の host での取得 | 自分で管理する機械の cron で取得し、結果を repository に push する |
| E | 複数の仕組みを組み合わせる(冗長化) | 例: A と C を併用する。どの経路で取得しても、記録の形式と窓の判定は同じにする |
| F | 取得の監視と通知(補助) | 窓の途中で「まだ使える取得がない」ことを検出して通知する。救済のための取得はしない(原則 3) |

## 6. 候補の比較の観点(評価はまだしていない。むすびさんと決める)

| 観点 | 確かめること |
|---|---|
| 監査可能性 | 取得の時刻と内容が、第三者に照合できる証跡(server 側の時刻、SHA-256、run の provenance)で残るか。どの経路の取得かが記録されるか |
| 障害耐性 | 1 つの仕組みが止まっても、窓の中の取得が残るか。単一障害点の数 |
| 凍結との整合 | 取得経路そのものをコード(Code_SHA の対象)として固定できるか。凍結されていない経路で本番データを取らないこと |
| 秘密情報 | 外部から起動する場合の token の保管と権限の範囲。漏れたときの影響 |
| コスト | GitHub Actions の分数(公開 repository の扱い)、外部サービスの費用、self-hosted の機械の維持 |
| 運用の負担 | 純さんが日々しなければならない作業の有無。障害時の手順 |
| CFTC 側への負荷 | 取得の回数が増えたときの礼儀(取得の間隔、User-Agent の明示) |
| S0 への依存 | M1 の発行の起動を S0 から独立させるかどうか(範囲に入れるかも論点) |

## 7. Acceptance Gate(V2 で採用する前に満たす条件。閾値は空欄で、試験の前に決める)

1. **試験期間**: 連続 ___ 日以上(V1 とは分けた検証用の経路で行う)。
2. **窓の中の取得の成功率**: 試験期間の Origin のうち、T_info の窓に入った正常な取得がある割合が ___ % 以上。
3. **最悪の場合**: 連続して窓を外した日が ___ 日以下。
4. **冗長性**: E を採る場合、意図的に 1 つの経路を止めた試験でも、窓の中の取得が残ること。
5. **監査可能性**: すべての取得について、経路、run の provenance、server 側の時刻、SHA-256 が記録され、独立の検査で照合できること。
6. **分離**: 試験期間中、V1 の data/m1macro/ と ledger/ に、V2 の行が 1 つもないこと。これを機械で確認する。
7. **凍結**: V2 の取得経路のすべての部分が、V2 の Code_SHA の対象になっていること。

4. 候補の絞り込み: §5 のうち、どれを比較の対象として残すか。
