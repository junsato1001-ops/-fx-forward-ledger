## 3. 取得の窓、時刻の記録、使えるかの判定

### 3.1 窓(凍結済みの規則。変えない)

- Origin t の CFTC snapshot として使えるのは、取得の時刻が (T_info(t) − 6h, T_info(t)] にあるものだけ。
- T_info は Origin の日の 03:00 JST。窓は前日の 12:00Z から 18:00Z まで。
- 窓の中に複数あれば、最も遅いものを使う。

### 3.2 時刻と出所の記録(必須)

次の欄を別々に持つ。

| 欄 | 意味 |
|---|---|
| Retrieved_At_Runner | 取得した実行環境の時計の値 |
| Server_Anchored_At | 第三者が照合できる server 側の時刻 |
| Content_SHA256 | 取得した原ファイルの SHA-256 |
| Acquisition_Path_ID | 取得した経路 |
| Execution_ID | 取得した実行の ID |

- **最終的に採用する anchor の要件**: Content_SHA256 と server 側の時刻が、暗号学的に、または監査できる形で結び付いていること。
- 「実行した時刻」だけを示す証拠(外部の scheduler の実行記録など)は、それだけでは anchor にならない。取得した中身そのものを anchor したことにならないからである。

### 3.3 使えるかの判定(方向は決定済み。δ はまだ Freeze しない)

```
Retrieved_At_Runner ∈ (T_info − 6h, T_info]
かつ
Server_Anchored_At ≤ T_info + δ
```

- δ の値は、server anchor の方式を決めてから決める(§9.4)。
- 補足の検査(提案。§9.5): Retrieved_At_Runner と Server_Anchored_At の前後関係が崩れていないかを検査する。

## 7. Acceptance Gate(4 群。すべて AND で判定する)

### 7.1 Safety Gate — 1 件でも違反すれば FAIL

1. V1 の repository の data/m1macro/ と ledger/ に、V2 の行が 0 件であること(機械で確認する)。
2. Holdout には、取得でも計算でも一切触れないこと。
3. V2 の取得経路のすべての部分が、V2 の Code_SHA の対象であること。
4. すべての取得について、provenance(§3.2 の 5 欄)と、Content_SHA256 と時刻の結び付きが完全であること。

### 7.2 Reliability Gate(決定済み)

- **(N, k) = (60, 2)**: 60 回の試験で、失敗が 2 回以下なら PASS。
- **2 回続けて失敗したら、その時点で即 FAIL**(60 回の終了を待たない)。
- 二項分布で計算した運用特性(むすびさんが独立に再計算して一致を確認):
  - 真の成功率が 90% なら PASS する確率は約 5.30%(誤って採用する確率)。
  - 真の成功率が 98% なら PASS する確率は約 88.13%。
- **この Gate を通っても、成功率が 98% であることを 60 回で証明したことにはならない。** この Gate が示すのは、「成功率 90% 程度の経路を、約 5% の確率でしか誤って採用しない」ということまでである。
- **上の運用特性は、各回が独立だと仮定した参考値である。Failover Gate を通過しても、独立性が証明されるわけではない。** GitHub の障害のように複数の回にまとめて効く失敗があれば、実際の誤採用の確率は参考値より高くなりうる。
- 2 回連続で即 FAIL とする規則を加えたので、実際に PASS する確率は上の参考値より少し低くなる(より厳しい)。

### 7.3 Determinism / Audit Gate(v0.1 から変更なし)

- snapshot を選ぶ規則が V1 と同じであること。
- hash を計算し直すと一致すること。
- server anchor を取り直すと一致すること。
- 経路と実行の ID が、実在の記録と一致すること。

### 7.4 Failover Gate(v0.1 から変更なし)

- A だけを止める回と、C だけを止める回を、事前に固定する。
- 止めた回でも、もう一方の経路で窓の中の取得が成立すること。
- この Gate が確かめるのは冗長な経路が働くことであって、各回の独立性ではない(§7.2)。

## 9. server anchor の方式と δ(設計案。採否はむすびさんが決める)

### 9.1 3 つの方式で、中身と時刻がどう結び付くか

| 方式 | 中身と時刻の結び付き | 独立性 | 障害点 | 検証の方法 |
|---|---|---|---|---|
| **G. GitHub の server 側の証拠** | 取得した原ファイル(または Content_SHA256 を書いた記録)を commit し、push する。commit の tree は中身の git object hash を含むので、中身は commit に結び付く。push を受け付けた時刻は activity API の timestamp で照合できる。Freeze の記録で使った方法と同じ | GitHub に依存する(trigger の A と同じ failure domain) | GitHub、push の失敗、activity の保持期間(保証はない) | commit の tree の hash と、activity の after・before・timestamp を照合する(F8-a と同じ) |
| **R. RFC 3161 系の時刻証明** | Content_SHA256 に対して、時刻認証局(TSA)が署名付きの timestamp token を発行する。token の中に hash と genTime が入っているので、暗号学的に結び付く | GitHub から独立している。複数の TSA を使えば TSA どうしも独立にできる | TSA が落ちること、TSA の証明書の失効や信頼の扱い、外部への通信 | `openssl ts -verify` などで、token の署名と hash を TSA の証明書の鎖で検証する |
| **X. 外部の scheduler / provider の実行記録** | 実行した時刻は示せるが、**中身との結び付きはそれだけでは得られない**。中身を X の server 側の記録に残すしくみがなければ anchor にならない | GitHub から独立している | provider と、記録の保持 | provider の API の記録。中身との結び付きは G か R に頼ることになる |

### 9.2 案

- **Server_Anchored_At として認めるのは、G または R だけにする。** X は Execution_ID の裏付けとして記録するが、時刻の anchor としては使わない(§3.2 の要件による)。
- **1 回の取得につき、G と R の両方を試みる。** 有効な anchor が **1 つ以上**あれば、その取得には anchor があるとみなす。両方があればどちらも記録し、判定には早い方の時刻を使う。
  - 理由: 両方を必須にすると、2 つのどちらが落ちても失敗になり、単一障害点が増える。どちらか 1 つで足りるようにすれば、経路の冗長化(E)と同じ考え方で anchor も冗長になる。
  - 代わりの案: R を必須、G を補助にする。こちらは独立性が最も高いが、TSA が落ちたときに弱い。
- C の経路(GitHub の外で取得する場合)でも、R は使える。G は、取得したものを V2 の repository に push した時点で付く。

### 9.3 R(TSA)を使う場合に決めること

- 使う TSA(複数)と、それぞれの証明書の鎖を固定し、Code_SHA の対象にする。
- token の保存先(V2 の repository)と、検証の手順。
- TSA の genTime の精度(通常は秒単位)の扱い。

### 9.4 δ(候補。試験の前に固定する)

- **δ が守るもの**: 中身が T_info の時点までに存在したことを、server 側の証拠で裏付ける。δ を大きくすると、T_info を過ぎてから取得したものを runner の時計の誤りで窓の中に見せる余地が広がる。δ を小さくすると、push や TSA の遅れのために、正しい取得を落とすことが増える。
- **今ある材料**(V2 の試験 telemetry ではなく、V1 の既存の記録だけを使った): V1 の CFTC snapshot 6 件について、Retrieved_At から main への push の activity timestamp までの遅れは 5、4、3、2、2、4 秒だった(最大 5 秒)。この 6 件は、push が 1 回目で通った場合だけを表している。V1 の push は、拒否されると rebase して再試行する(最大 5 回)。
- 候補:
  - **δ = 60 秒**: 観測した最大値(5 秒)の約 12 倍。push の再試行が数回あっても多くは収まる。窓の外の取得が混じる余地は小さい。
  - **δ = 300 秒**: TSA の応答の遅れや、push の再試行が重なった場合にも余裕がある。そのかわり、検出できない時刻のずれの幅は 5 分になる。
- **提案は δ = 300 秒。** どちらの方式も「1 つ以上あれば足りる」ので、δ を超えて落ちる取得は、anchor の両方が遅れた場合だけになる。また §9.5 の補足の検査で、時計の大きなずれは別に止められる。
- δ は、この版の監査で採用が決まったら、Acceptance Gate とともに試験の前に固定する。試験 telemetry を見てから変えない。

### 9.5 補足の検査(提案)

- **時計の前後関係**: Server_Anchored_At ≥ Retrieved_At_Runner − ε とする。ε は runner の時計の許容誤差で、案は 5 秒。anchor が取得より大きく前にあるなら、時計がおかしいので失敗にする。
- **anchor までの遅れの上限**: Server_Anchored_At − Retrieved_At_Runner ≤ δ。§3.3 の条件と合わせると、T_info の直前に取得したものは、T_info + δ までに anchor されなければならない。
- どちらも fail-closed にする。満たさない取得は「使えない」と記録し、救済はしない。
